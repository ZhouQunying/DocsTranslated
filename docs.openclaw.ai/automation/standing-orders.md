# 常驻命令

## 架构精读

> 跳过不影响阅读翻译正文。

### 为什么 agent 需要"常驻命令"而非每次提示？

传统 agent 工作流：用户每次发指令，agent 执行，然后空闲。问题是常规工作（周报、收件箱整理、系统监控）容易被遗忘或延迟，用户成了瓶颈。常驻命令走了另一条路：定义**计划**（做什么、何时做、何时升级），agent 在边界内自主执行。这就像军队的"交战规则"（Rules of Engagement）——士兵不需要每次开枪都请示，但有明确的开火条件、升级路径和禁止行为。好处是 agent 不再被动等待指令，常规工作按日程自动执行；用户只在异常时介入。

第二个设计：计划四要素。每个常驻命令指定**范围**（agent 被授权做什么）、**触发器**（何时执行：日程、事件或条件）、**审批门控**（什么需要人类签字）、**升级规则**（何时停下来求助）。这就像微服务的 SLA 定义——每个服务声明自己的可用性目标、自动扩缩容条件、人工介入阈值。好处是 agent 的行为边界是显式的、可审计的、可测试的。

第三个边界：执行-验证-报告模式。每个任务遵循三步循环。先执行实际工作，不只是确认指令。再验证结果正确，如文件存在、消息已送达、数据已解析。最后向所有者报告做了什么和验证了什么。这防止最常见的 agent 失败模式：确认任务但不完成。就像单元测试的 AAA 模式（Arrange-Act-Assert）——不只是调用方法，还要断言结果符合预期。

---

常驻命令为 agent 授予**永久操作权限**以执行已定义的计划。无需每次给出单独任务指令，你定义具有明确范围、触发器和升级规则的计划——agent 在这些边界内自主执行。

这是告诉助手"每周五发周报"与授予常驻权限的区别："你负责周报。每周五编译、发送，只在异常时升级。"

## 为什么使用常驻命令

**无常驻命令时：**

- 你必须为每个任务提示 agent
- agent 在请求之间闲置
- 常规工作被遗忘或延迟
- 你成了瓶颈

**有常驻命令时：**

- agent 在定义的边界内自主执行
- 常规工作按日程自动执行无需提示
- 你仅在异常和审批时介入
- agent 高效利用闲置时间

## 工作原理

常驻命令在 [agent 工作区](/concepts/agent-workspace)文件中定义。推荐方法是将它们直接包含在 `AGENTS.md` 中（每次会话自动注入），这样 agent 始终将它们保持在上下文中。对更大的配置，也可放在专用文件如 `standing-orders.md` 中并从 `AGENTS.md` 引用。

每个计划指定：

1. **范围** — agent 被授权做什么
2. **触发器** — 何时执行（日程、事件或条件）
3. **审批门控** — 什么需要在行动前人类签字
4. **升级规则** — 何时停下来求助

agent 每次会话加载这些指令时读取工作区引导文件，并结合 [cron 作业](/automation/cron-jobs) 实现时间执行。

> **提示：** 将常驻命令放在 `AGENTS.md` 中以确保每次会话加载。工作区引导自动注入 `AGENTS.md`、`SOUL.md`、`TOOLS.md`、`IDENTITY.md`、`USER.md`、`HEARTBEAT.md`、`BOOTSTRAP.md` 和 `MEMORY.md`——但不注入子目录中的任意文件。

## 常驻命令结构

```markdown
## 计划：周状态报告

**权限：** 编译数据、生成报告、交付给利益相关者
**触发器：** 每周五下午 4 点（通过 cron 作业执行）
**审批门控：** 标准报告无需审批。异常标记供人类审查。
**升级：** 如果数据源不可用或指标异常（偏离正常值 >2σ）

### 执行步骤

1. 从配置的源拉取指标
2. 与上周和目标比较
3. 在 Reports/weekly/YYYY-MM-DD.md 中生成报告
4. 通过配置的渠道交付摘要
5. 记录完成到 Agent/Logs/

### 禁止行为

- 不向外部方发送报告
- 不修改源数据
- 指标差时不跳过交付——如实报告
```

## 常驻命令加 cron 作业

常驻命令定义 agent **被授权做什么**。[Cron 作业](/automation/cron-jobs)定义**何时发生**。它们协同工作：

```
常驻命令："你拥有每日收件箱整理"
    ↓
Cron 作业（每天早 8 点）："按常驻命令执行收件箱整理"
    ↓
Agent：读取常驻命令 → 执行步骤 → 报告结果
```

cron 作业提示应引用常驻命令而非重复它。

## 执行-验证-报告模式

常驻命令与严格的执行纪律结合时效果最好。常驻命令中的每个任务应遵循此循环：

1. **执行** — 做实际工作（不只是确认指令）
2. **验证** — 确认结果正确（文件存在、消息已送达、数据已解析）
3. **报告** — 告诉所有者做了什么和验证了什么

```markdown
### 执行规则

- 每个任务遵循执行-验证-报告。无例外。
- "我会做"不是执行。做了，然后报告。
- 没有验证的"完成"不可接受。证明它。
- 如果执行失败：用调整的方法重试一次。
- 如果仍然失败：报告失败及诊断。永不静默失败。
- 永不确定重试——最多 3 次尝试，然后升级。
```

此模式防止最常见的 agent 失败模式：确认任务但不完成。

## 多计划架构

对管理多个关注点的 agent，将常驻命令组织为具有明确边界的独立计划：

每个计划应有：

- 自己的**触发节奏**（每周、每月、事件驱动、持续）
- 自己的**审批门控**（有些计划比其他需要更多监督）
- 清晰的**边界**（agent 应知道一个计划在哪里结束、另一个在哪里开始）

## 最佳实践

### 做

- 从窄权限开始，随着信任建立扩展
- 为高风险操作定义显式审批门控
- 包含"禁止行为"段落——边界与权限同等重要
- 结合 cron 作业实现可靠的时间执行
- 每周审查 agent 日志验证常驻命令被遵循
- 随需求演进更新常驻命令——它们是活文档

### 避免

- 第一天就授予广泛权限（"做你认为最好的"）
- 跳过升级规则——每个计划需要"何时停下来问"条款
- 假设 agent 会记住口头指令——把所有东西放在文件中
- 在单一计划中混合关注点——不同域用不同计划
- 忘记用 cron 作业执行——没有触发器的常驻命令变成建议
