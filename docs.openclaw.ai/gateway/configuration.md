# Configuration

## 架构精读

> 跳过不影响阅读翻译正文。

### JSON5 而非纯 JSON——配置文件的人性化

OpenClaw 的配置文件 `~/.openclaw/openclaw.json` 使用 **JSON5** 格式。JSON5 是 JSON 的扩展,允许:
- **注释**(如 `// 这是注释`): 可以标注为什么这样配置
- **末尾逗号**(如 `{ a: 1, b: 2, }`): 添加/删除字段时不用管逗号
- **无引号的键**(如 `{ model: "gpt-4" }`): 写起来更简洁

**为什么不用纯 JSON?** 纯 JSON 不允许注释和末尾逗号。配置文件经常需要注释(解释为什么选这个模型、为什么关闭某个功能),纯 JSON 做不到。末尾逗号的问题更实际: 添加新字段时,如果上一个字段没有逗号,JSON 解析就报错。JSON5 的末尾逗号让编辑配置文件更不容易出错。

**为什么不用 YAML?** YAML 虽然支持注释,但语法更复杂(缩进敏感,`-` 和 `:` 容易混),而且 JSON5 是 JSON 的超集,所有 JSON 文件都是合法的 JSON5。选择 JSON5 = JSON 的简单 + YAML 的人性化,没有 YAML 的语法陷阱。

### 四种配置方式——适配不同用户

OpenClaw 提供四种修改配置的方式:
1. **交互式向导**(`openclaw configure`): 一步步问答,适合新手
2. **CLI 单行命令**(如 `openclaw models set gpt-4`): 改单个字段,适合脚本
3. **Control UI**(web 界面): 可视化编辑,适合不喜欢命令行的用户
4. **直接编辑文件**: 用编辑器改 `openclaw.json`,适合高级用户

**为什么需要四种?** 因为用户群体差异大。新手不知道配置文件在哪、格式是什么,需要向导。运维人员写自动化脚本,需要 CLI 单行命令。普通用户不想记命令,需要 GUI。开发者习惯直接编辑文件,觉得向导和 GUI 都是多余的。四种方式覆盖四种用户,不强迫任何人用不习惯的方式。

### 热更新 vs 重启——哪些配置能即时生效

配置分为两类:
- **热更新**(hot-apply): 修改后即时生效,不需要重启 Gateway
- **需要重启**: 修改后必须重启 Gateway 才能生效

**为什么不是所有配置都能热更新?** 因为有些配置影响 Gateway 的核心运行状态,修改后需要重新初始化:
- **能热更新的**: 模型选择、fallback 列表、tool 开关——这些是"策略"类配置,Gateway 每次请求都会读取,改了立刻生效
- **需要重启的**: 监听端口、TLS 证书、数据库连接——这些是"基础设施"类配置,Gateway 启动时就固定了,运行中不能改

**这跟 nginx 的 reload 是一个思路**——`nginx -s reload` 可以让配置变更生效,但不是所有配置都能 reload。改了 `listen` 端口需要 restart,改了 `proxy_pass` 可以 reload。OpenClaw 也是同样的设计: 策略类配置热更新,基础设施类配置需要重启。

**用户怎么知道哪些能热更新?** 文档有明确列表。如果不确定,改完后看 Gateway 日志——热更新的配置会显示"config reloaded",需要重启的会显示"restart required"。

### Symlink 不被支持——配置路径必须是真实文件

配置文件路径必须是**真实文件**(regular file),不能是 symlink(符号链接,指向另一个文件的快捷方式)。

**为什么不支持 symlink?** 因为 OpenClaw 需要监控配置文件变更(用于热更新)。文件监控工具(如 `inotify`)对 symlink 的行为不一致——有些监控 symlink 本身,有些监控 symlink 指向的目标文件。为了避免"改了配置但 Gateway 没检测到"的问题,OpenClaw 要求配置文件是真实文件,不做 symlink 解析。

**如果你有 symlink 的需求**(如多个机器共享配置),用 `rsync` 或 `scp` 复制文件,不要用 symlink。
